1 · What changed in the knowledge bases

All changes were made directly in Supabase on 15 Aug 2026. A full pre-change snapshot is committed at backend/supabase/kb-backup-2026-08-15.json — 10 KBs, 87 room assignments, 42 property rooms, 44,279 characters of content. Nothing is unrecoverable.

Removed 45 unmatchable room assignments

The Hotel Molo Residence KB had 54 rooms attached, but the agent looks up a different table (property_rooms) when identifying a guest. 45 of those assignments existed only in the KB list, so the agent answered “I couldn't find a room X in any Molo property” even though a KB existed.

The list was a channel-manager export pasted onto the wrong KB. It contained other properties' units:

11 Ap 101 + … 28 Ap 402                         → Molo / Riviera Apartments

02 Classic … 10 Classic                         → duplicates of rooms 2–10

Verified before deleting that 0 would orphan a real room, and after deleting that every real room resolves to exactly one KB. Assignments went 87 → 42.

Removed three test lines from the general KB

These were loaded on every call:

  • what colour are the carpets? --> the carpets are orange and fluffy
  • we have a policy that allows you to ride skateboards inside teh hallways
  • loud hours : 3am to 3pm — the dangerous one. It reads as “you may be loud from 3am”, the inverse of a quiet-hours policy.

General KB content: 1,780 → 1,596 characters. Nothing real was touched.

Confirmed: one room can never be in two knowledge bases. There is a unique index on (property_id, room_number). This was verified by attempting an actual duplicate insert, which was rejected:

ERROR 23505: duplicate key violates
"knowledge_base_rooms_property_room_uniq"

Different properties can each have their own room 4 — that's allowed and correct. The dashboard also pre-checks and shows a conflict message before saving.

One gap in that guarantee, currently unreachable. property_id is nullable, and Postgres treats NULLs as distinct in a unique index. The edge API still accepts a legacy roomNumbers: string[] payload that writes property_id = null — two of those for the same room would both be allowed. The dashboard sends the scoped {property_id, room_number} shape, so the UI can't trigger it, and there are 0 such rows today. Worth closing eventually.

2 · How the agent uses knowledge bases

1
Call starts — general KB loaded
The default general KB is read from Supabase into memory. It is deliberately not put in the system prompt — that bloated time-to-first-token and pulled the model toward Polish.
2
Guest identified — room KB swapped in
identify_guest matches the room against property_rooms, then the kb_for_room view returns the property KB plus any exception KB. They are merged with priority labels:
### ROOM-SPECIFIC INFO (overrides the general info below) ← priority ≥ 3 --- ### GENERAL PROPERTY INFO ← priority 2
3
General KB appended fixed 15 Aug
Previously the room KB replaced the general one and it was gone for the rest of the call — kb_for_room joins on kb.property_id = p.id and a general KB has property_id NULL, so it can never come back. A guest could get their Wi-Fi password and then be told we have no info about locations or booking. The general KB is now appended after the room KB, so room-specific values still win.
4
Question asked — Gemini searches the text
search_kb sends the question + the whole loaded KB to Gemini 2.5 Flash on Vertex AI (temperature 0, max 300 tokens, 10s timeout). This is a separate model call — the KB is never seen by Gemma, and never goes through LiveKit. Gemma only ever sees Gemini's short answer.
5
Fallbacks
Gemini error or timeout → naive keyword paragraph scoring over the same text. Nothing found → NO_KB_MATCH, and the agent asks for a room number to try again. Answers are memoized per call and cleared when the KB swaps, so dashboard edits take effect on the next call with no deploy.

Editing a KB in the dashboard takes effect immediately — on the next call. There is no cache to clear and no redeploy. The agent reads Supabase at call start.

7 · Notes for the developer

Two deploy paths — they are not the same

Agent (backend/agent/) ships from your local directory via lk agent deploy. Git is not involved; uncommitted changes go live immediately.

Frontend (frontend/) builds from GitHub main via Render. Nothing reaches the dashboard until it is committed and pushed.

Mixing these up cost real time — dashboard changes looked like they'd done nothing because they were never pushed.

Deploying the agent — a bare lk agent deploy is wrong

The repo-root Dockerfile still launches src/agent.py (the retired speech-to-speech agent) and root livekit.toml points at CA_9A3cUKL9gVwz, which no longer exists. Swap the pipeline files in, then restore:

cd backend/agent
cp pipeline/Dockerfile Dockerfile
cp pipeline/livekit.toml livekit.toml
lk agent deploy --project molo-residence
git checkout Dockerfile livekit.toml

Live agent: CA_9DeKbNqCaYHQ (molo-gemma). Always pass --project molo-residence — four other LiveKit projects share the login. Check lk room list for live calls first; a deploy restarts the agent.

Never edit agent.py

It's imported by the pipeline agent and treated as read-only. All pipeline behaviour lives in agent_pipeline.py, including overrides of transfer_call, _answer_kb and _before_tool. The prompt is in pipeline_prompt.py — agent.py's own INSTRUCTIONS and GREETING are unused and still say “Mili”.

TTS failure is a synthesis-time event

An unusable voice ID does not raise at construction — inference.TTS builds fine and only errors on the first real synthesis, per utterance. A construction-time try/except never fires and the caller hears silence for the whole call. This took the line down twice on 15 Aug. The fix is tts.FallbackAdapter, which fails over per-utterance, with a known-good floor voice behind the primary. Guarded by test_tts_failover_happens_at_synthesis_not_construction.

Provider voice libraries vs default voices

LiveKit Inference only serves each provider's default voice set. A voice picked from ElevenLabs' community voice library returns BAD_REQUEST: A voice with voice_id … does not exist at call time. That's why the agent is on Cartesia Sonic-3.5 rather than ElevenLabs. Separately, every elevenlabs/* model on the Inference gateway retires 31 Aug 2026.

Known open issues

  • Memory sits at 530–566 MB against a 500 MB warning threshold for entire calls. No hard limit is set, and it hasn't caused a failure — but it warns every 5 seconds and is worth watching.
  • Deepgram multi occasionally mis-transcribes short English utterances as Russian Cyrillic. It cannot be restricted to a language subset. AssemblyAI can do that (language_codes) but doesn't support Polish at all on Inference.
  • Virtual numbers (Hushed etc.) have produced both a mid-call drop (CLIENT_INITIATED, carrier-side) and an SMS accepted by Telnyx that never arrived. Test from a real mobile.
  • SMS “sent” means queued, not delivered — send_sms returns true when Telnyx hands back a message ID. There is no delivery-receipt handling.
  • Two Deno route tests for the transcript-delete endpoint are written but never run — deno wasn't installed on the machine they were authored on.
